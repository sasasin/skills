# quick-research — 5分で「根拠つきの見立て」を返す

目的: 検索10回・本文取得4件・約5分の予算で、結論→根拠→出典の短いレポートを返す。
深掘りより「取りこぼしのない地図」と「数字・日付の正確さ」を優先する。

## 使う手段（ツール名は環境しだい。名前で決め打ちしない）

このスキルが要るのは3つの**能力**だけ。能力を持つツールを実行環境のツール一覧から選んで使う。特定の製品名を前提にした手順は書かない。

| 能力 | 環境でのよくある名前 |
|---|---|
| キーワードでWeb検索し、記事の題名・URL・日付・抜粋を得る | Pi `web_search` / Claude Code `WebSearch` / Codex CLI `web_search` / Gemini CLI `google_web_search` / OpenCode `websearch` / MCP 系 `brave_web_search`・Tavily `web_search`・Exa `web_search_exa` |
| 特定URLの本文を読む（検索で足り無い時だけ） | Pi `web_fetch`（拡張があれば `fetch_url`）/ Claude Code `WebFetch` / Gemini CLI `web_fetch` / OpenCode `webfetch` / Cline `fetch_web_content`・`fetch_web` / MCP 系 `fetch` / 該当ツールが無ければ shell の `curl -sL '<url>'` |
| 今日の日付を確定する | bash `date`（Windows PowerShell なら `Get-Date`） |

同じ能力のツールが複数あるときは、**検索結果のURLと日付をそのまま返す方**を使う（後でSourcesに書くため）。本文取得は、JSレンダリングが必要なページを除けば shell の `curl` でも代替できる。

該当ツールが見つからないときの順序:
1. ツール一覧から `web` / `search` / `fetch` / `browse` を含む名前を探す。`web_search` と `websearch` は別ツールなので名前の完全一致は求めない
2. 素の検索ツールが無く、検索込みで文章を返すツール（例: Pi の `web_research`）しかないときは、それを検索の下請けに使う。ただし**出典URL・日付・数値を返させる**（リード表とSourcesは自分で作る。ツール側の要約をそのまま答えない）
3. 検索はあるが本文取得が無いときは `curl -sL` で取る。HTMLが重すぎる/空なら、そのページは諦めて別ソースに当たる
4. 検索も取得も無いときは、Webアクセスが無いことをユーザーに伝えて止める。記憶や推測で「最新」を書かない

## 予算（厳守）

予算はツール名ではなく**検索クエリ数と取得ページ数**で数える。1回の呼び出しで複数クエリを渡せるツールなら1回にまとめ、1クエリずつのツールなら同じ本数を順に投げる。

| 項目 | 上限 |
|---|---|
| 検索ラウンド | 3（R1: 広く / R2: 裏取り / R3: 穴埋め・任意） |
| 検索クエリ総数 | 10（ツールが1回に何クエリ受け取れても、総数は10） |
| 本文取得 | 4ページ（1ページは要点だけ読む。全文要約しない） |
| 思考 | 各ステップ数行。ページごとの長い要約・言い換えはしない |

予算に達したら、集まった材料で書く。足りない点は「未確認」と明記する。

## 手順

### Step 0: 枠決め（検索前、30秒）
1. `date` を実行し、今日の日付を確定する（shell が無ければ PowerShell の `Get-Date`。それも無ければ環境から確認できる日付を書き、不明ならその旨をレポートに記す）。以降「最新」はこの日付基準。
2. 依頼を次の3つに分解し、メモに書く:
   - **事実**: 確認すべき数値・日付・出来事（例: 指数の水準、いつ、どれだけ動いたか）
   - **なぜ**: 原因・要因の候補（まだ仮説でよい）
   - **次**: 今後の注目点・イベント
3. 「答えるのに必要な主張」を3〜5個、箇条書きで決める。これが停止条件になる。

### Step 1: 広く撒く（R1、3〜4クエリ）
角度を変えたクエリを投げる（1回で複数クエリ渡せるツールならまとめる）。言い換え違いではなく**情報源の種類**を変える:
- 英語ニュース: `<対象> <月 年>` や `<対象> stocks fall <日付>` など、日付入り
- 日本語ニュース: `<対象> 要因 <月>`
- 一次・専門筋: 取引所・公的機関・業界団体の解説（例: `Cboe <対象> week of`、`<機関> statement`）
- 識者の見方: `<対象> strategists analysts say`
時事なら検索ツールの**新着絞り込み**を使う。呼び名と値は環境による（例: `recencyFilter: "week"` / `"month"`、`freshness`、`timeRange`、日付範囲の引数）。絞り込みオプションが無いツールでは、クエリに「月 年」や具体的な日付を入れて新しさを出す。

スニペットを読んで**リード表**を作る（ページはまだ開かない）:
```
| リード（固有名詞・出来事・数値） | 出典 | 日付 |
```
- 1つの記事が**ついでに触れた**別要因（例:「午後は原油高も重しに」）は必ずリードに入れる。ここを拾えるかで浅さが決まる。
- **日付チェック**: 前年同月など古い記事は捨てる。タイトルの年まで確認する。

### Step 2: 裏取りと深掘り（R2、3〜4クエリ + 本文2〜3件）
- 本文取得は、前のStepで得たURLをそのまま使う（検索を経由して開く必要はない）。
- リードのうち「なぜ」に効きそうなもの上位3〜4個に、1個1クエリで個別に当てる（まとめて1クエリにしない）。
- 本文を取得するのは次の組み合わせで最大3件:
  1. 主要メディアの当日まとめ記事（全体像と数値）
  2. 一次・専門筋（取引所レポート、公的発表、当事者の発言）
  3. 別言語・別視点の記事（偏りの補正）
- 本文からは「主張・数値・誰の見方か・日付」だけを抜き出してメモに追記する:
```
- [要因A] 主張 … / 数値 … / 誰が言った … / 出典URL / 日付
```

### Step 3: 穴埋め（R3、任意・最大2クエリ + 本文1件）
Step 0 の「必要な主張」のうち、出典が1つもないものだけを狙う。
全部埋まっていれば飛ばす。

### Step 4: 検証（書く前に1分）
- [ ] 数値ごとに「終値か日中か」「いつ時点か」が明確
- [ ] 出典同士で数値が食い違う場合は両方書くか、新しく一次に近い方を採用し理由を書く
- [ ] 要因ごとに少なくとも1つ出典がある。推測は「〜と見られる（筆者推測）」と区別
- [ ] 反対の見方・楽観論を1つは入れる
- [ ] 古い記事（前年など）を混ぜていない

## 出力フォーマット（日本語、スマホ1〜2画面）
```
**結論（1〜2文）**: 何が起きていて、主因は何か。

**現状の数字**
- 水準・変化・日付（終値/日中を明記）

**関係者/有識者/実務者が挙げる要因**
1. **要因名（最大要因から）**
   - 具体的な出来事・数値
   - 誰がどう見ているか（機関名・人名）
2. …（3〜5個）

**見方の分かれ目／反対意見**
- …

**今後の注目点**
- 日付つきイベント

Sources:
- [タイトル](URL)
```
- 引用は短く。基本は自分の言葉で要約する。
- 出典に無いことを事実として書かない。
